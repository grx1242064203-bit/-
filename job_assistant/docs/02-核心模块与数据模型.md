# 02 - 核心模块与数据模型

## 1. 数据库 Schema（三表设计）

数据库文件：`data/jobs.db`（SQLite）

### 1.1 companies 表 — 公司元数据

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| name | TEXT UNIQUE | 公司名称 |
| industry | TEXT | 归一化行业（18 类） |
| company_type | TEXT | 归一化企业性质（5 类：国央企/民企/外企/事业单位/其他） |
| locations | TEXT | 工作地点（逗号分隔） |
| has_announcement | INTEGER | 是否有校招公告（默认 1） |
| announcement_url | TEXT | 公告链接（取最新） |
| last_sync_time | TEXT | 最近同步时间 |
| source | TEXT | 数据来源（默认 feishu） |

### 1.2 announcements 表 — 招聘公告（后台中间表）

每条记录 = 一个公司的一个招聘链接。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | 自增主键 |
| company | TEXT | 公司名称（关联 companies.name） |
| job_title | TEXT | 原始多岗位拼接标题（飞书导入） |

| detail_analyzed | INTEGER 是否已做 AI 分析（0/1） |
| analysis_status | TEXT | 分析状态（见下方枚举） |

**analysis_status 枚举**：

| 值 | 含义 | 可恢复 |
|----|------|--------|
| `success` | 成功拆分出岗位 | - |
| `fetch_blocked` | 微信反爬拦截 | ✅ 换 IP/降速重试 |
| `fetch_failed` | 抓取失败 | ✅ 重试 |
| `content_invalid` | 抓到无效正文（如验证页） | ⚠️ 需改进抓取 |
| `llm_parse_empty` | 内容有效但 LLM 未拆出岗位 | ✅ 重试 + 优化 prompt |
| `not_current_grade` | 非本届校招 | ❌ 过滤 |

### 2.2 fetch_announcements.py — 阶段一：并发抓取

**职责**：用 Playwright 并发抓取公告正文+图片，写入 `fetch_results.jsonl`。

**关键参数**：
- `--workers N`：并发线程数（默认 5）
- `--limit N`：最多处理条数

**JSONL 输出格式**：
```json
{
  "dedup_hash": "...",
  "company": "...",
  "job_title": "...",
  "url": "...",
  "text": "公告正文文字",
  "images": ["图片url1", ...],
  "status": "ok" | "blocked" | "fetch_failed" | "link_invalid" | "no_url",
  "is_wechat": true
}
```

**反爬策略**：
- 微信 UA 伪装
- 随机延迟 2-5 秒
- 图片压缩到 600px，最多 4 张

**断点续传**：启动时加载 `fetch_results.jsonl` 中已有的 dedup_hash，跳过已抓取。

### 2.3 analyze_daemon.py — 阶段二：LLM 分析守护进程

**职责**：tail -f 模式持续消费 `fetch_results.jsonl`，调用 LLM 拆分岗位。

**运行模式**：
- 与阶段一并行运行
- 检测阶段一结束 + 120 秒无新记录后自动退出
- 去重：查 jobs 表 `detail_analyzed=1` 的 dedup_hash

**分析流程**：
1. 正文 < 50 字 → DeepSeek-VL OCR 图片
2. DeepSeek 拆分具体岗位（25+ 维度）
3. 每个岗位 insert 到 jobs 表
4. 更新 announcements.analysis_status

### 2.4 user_matcher.py — 用户-岗位匹配

**两阶段匹配**：

**阶段一：规则预筛（8 个维度）**
1. 届数范围：用户毕业年份 ∈ [target_min_grade, target_max_grade]
2. 行业：industry ∈ target_industries
3. 公司类型：company_type ∈ preferred_company_types
4. 学历：用户学历 ≥ min_education
5. 城市：city 命中 target_cities
6. 专业：major_required 与用户专业有交集
7. 技能：hard_skills 与用户 core_skills 有交集
8. 证书：用户持有岗位要求的 certifications

**阶段二：AI 评分**
- 调用 `score_job()` 生成相关性评分
- 过滤评分 < 30
- 每公司限 5 个（按评分降序取前 5）

### 2.5 scorer.py — 评分引擎

**评分维度（满分 100）**：

| 维度 | 分值 | 说明 |
|------|------|------|
| 方向匹配 | 0-40 | 命中用户目标方向=40，部分=25，未命中=10 |
| 平台/公司 | 0-20 | 目标公司=20，其他=10 |
| 经验匹配 | 15 | 校招统一满分 |
| 技能匹配 | 0-15 | 每命中一个技能+3，上限 15 |
| 学历匹配 | 3-10 | 博士=10，硕士=7-10，本科=10 |
| 专业匹配 | 0-10 | 匹配=10，不匹配=0，信息不足=5 |
| 行业匹配 | 0-10 | 命中=10，未命中=0，不限=5 |
| 证书加分 | 0-5 | 持有岗位要求证书+5 |

**综合推荐度**：
| 评分 | 推荐度 |
|------|--------|
| ≥70 | 优先申请 |
| ≥50 | 可申请 |
| ≥30 | 观望 |
| <30 | 跳过 |

### 2.6 daily_runner.py — 每日任务执行

**单用户流程**：
1. UserRunLock（用户级文件锁，防并发）
2. 确保飞书表字段完整（_ensure_table_fields）
3. 匹配岗位（user_matcher）
4. 分离管培岗位 → 管培项目表
5. 去重写入主表（_dedupe_and_write）
6. 复查在招状态，归档已关闭（_recheck_and_archive）
7. 生成日报文档（_create_daily_report）
8. 飞书卡片推送（_send_daily_card）
9. 微信推送（可选）
10. 校招截止提醒（3 天内）
11. 投递跟踪（已投递岗位关闭通知）

## 4. 飞书多维表格 Schema

定义在 `schema.py`，每个用户有 3 张表：

### 4.1 岗位表（JOB_FIELDS）

核心字段：岗位标题、公司、行业、公司类型、难度、地点、薪资、学历要求、JD摘要、JD链接、投递截止日期、岗位类别、相关性评分、综合推荐度、简评、申请建议、申请状态、应届窗口、管培项目等。

### 4.2 已关闭岗位表（CLOSED_JOB_FIELDS）

### 4.3 管培项目表（MT_TABLE_FIELDS）

项目名称、公司、管培类型、届数、招聘阶段、地点、项目介绍、申请要求、网申链接、截止日期等。

## 5. 去重机制

### 5.1 数据库级去重

`dedup_hash` UNIQUE 约束：`md5(company|title 归一化)` 前 16 位。

归一化规则（`_normalize_for_hash`）：
- 去除括号及内容
- 去除空白
- 转小写
- 去除"招聘/急招/热招/校招/应届"等后缀

### 5.2 用户级去重

每个用户有 `data/hashes/{user_id}.json`，记录已写入飞书的岗位 hash。写入前检查：
1. 飞书主表 + 已关闭表中是否已有该 hash
2. 本地 hash_store 中是否已有

两者都没有才写入。

## 6. 并发安全

| 场景 | 机制 |
|------|------|
| 用户配置并发写 | `UserStore._file_lock`（fcntl 排他锁 + 全量重载） |
| 用户采集并发 | `UserRunLock`（fcntl 非阻塞排他锁） |
| hash 文件并发写 | `HashStore._file_lock` + 持锁重载 |
| 抓取-分析并发 | JSONL append-only 原子写入，分析只读 |
