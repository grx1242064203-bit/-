## 2026-09-26 — 校招总数据库输出字段补全 + 飞书表自动字段迁移

**变更类型**：P0 数据字段完整性修复 + 老用户表自动迁移

### 背景
校招用户的岗位数据来自总数据库（`job_db.py`，中心化采集）。用户反馈飞书岗位表中缺少关键信息：岗位的 JD 摘要、公司所属行业、公司类型、申请难度、岗位发布时间。经排查，`score_job()` 的返回字典未包含这 5 个字段，且 `user_matcher.py` 未将主库的 `jd_summary` 透传给评分器，导致 LLM 分析失败时 `JD摘要` 为空。

### 修复内容

1. **`schema.py` — 新增 3 个字段定义**
   - `行业`（text，公司所属行业，来自公司库）
   - `公司类型`（text，民企/国央企/外企）
   - `难度`（text，最激烈/较为激烈/中等难度/较低难度）
   - `JD摘要`、`发布时间` 已存在，无需新增
   - 新字段紧随 `公司` 字段之后，便于用户阅读

2. **`user_matcher.py` — 透传主库字段到评分器**
   - `_score_and_rank()` 构建 `job_for_score` 时新增透传：`jd_summary`、`industry`、`company_type`、`difficulty`
   - 修复 `JD摘要` 降级 bug：此前未传 `jd_summary`，LLM 分析失败时摘要为空；现在降级到主库预生成的摘要

3. **`scorer.py` — 输出字段补全**
   - `score_job()` 返回字典新增 `行业`、`公司类型`、`难度`，值源自主库透传
   - `JD摘要` 降级链明确：LLM 深度分析 → 主库 `jd_summary` → 空

4. **`daily_runner.py` — 飞书表自动字段迁移**
   - 新增 `_ensure_table_fields()` 方法：每次任务前对比 `JOB_FIELDS` 与飞书表现有字段，自动 `create_field` 补建缺失字段（幂等，已有则跳过）
   - 解决老用户表缺少 `行业/公司类型/难度` 导致写入失败的问题
   - 同时覆盖主表和已关闭表

### 字段流转链路
```
主库 jobs 表          user_matcher          scorer              飞书表
─────────────        ─────────────         ──────────          ──────
jd_summary    ──→  jd_summary(透传) ──→  JD摘要(降级兜底) ──→  JD摘要 ✓
industry      ──→  industry         ──→  行业              ──→  行业 ✓
company_type  ──→  company_type     ──→  公司类型           ──→  公司类型 ✓
difficulty    ──→  difficulty       ──→  难度              ──→  难度 ✓
publish_time  ──→  posted           ──→  发布时间           ──→  发布时间 ✓
```

## 2026-09-26 — 校招来源过滤修复 + 服务器同步流程规范化

**变更类型**：P0 领英等黑名单域名过滤修复 + 部署流程文档强化

### 背景
用户反馈校招岗位采集结果中仍出现大量领英（LinkedIn）链接。经排查，原有的 `_is_allowed_campus_source()` 白名单过滤在本地测试有效，但**未同步到生产服务器**，导致线上仍运行旧代码。这暴露了"本地修改 ≠ 服务器生效"的流程缺陷。

### 修复内容（`collector.py`）

1. **搜索 API 层排除（第一道防线）**
   - `TavilySearchProvider` / `SerpApiSearchProvider` 新增 `exclude_domains` 参数
   - 校招用户的**所有搜索查询**均传入 `CAMPUS_BLOCKED_DOMAINS`，在搜索 API 层就排除领英等平台
   - Tavily 用 `exclude_domains` 参数，SerpAPI 用 `-site:` 操作符

2. **结果层白名单过滤（第二道防线）**
   - `_is_allowed_campus_source()` 开头新增硬黑名单检查：遍历 `CAMPUS_BLOCKED_DOMAINS`，命中即拒绝
   - 黑名单从 12 个扩展到 18 个，新增领英变体：`linkedin.cn`、`lnkd.in`，以及 `monster.com`、`careerbuilder.com`、`kanzhun.com`、`前程无忧`

3. **入库前二次校验（第三道防线）**
   - 采集结束后遍历最终 jobs 列表，检查每个 `jd_url` 是否含黑名单域名
   - 若有漏过则 `logger.error` 告警，否则打 `✓` 日志

4. **可观测性**
   - 新增来源过滤统计日志：`[校招来源统计] 允许来源: N, 拦截黑名单: M, 最终入库: K`

### 部署流程规范化（`05-部署运维SOP.md`）

新增「3. 服务器同步核心原则」章节，强调：
- **第一性原则：本地代码修改 ≠ 服务器生效**，所有改动必须 `scp` 上传 → 语法检查 → 重启服务 → 健康检查 → 生产验证
- 明确服务器信息（阿里云轻量服务器 `47.250.216.165`，域名 `zhaopin-helper.xyz`，路径 `/opt/job_assistant`）
- SSH 通过 HTTP 代理 CONNECT 隧道连接（`ProxyCommand nc -X connect -x 127.0.0.1:18080 %h %p`）
- 部署 Checklist 6 项必须逐项确认
- 修正部署脚本为 `scp` 上传方式（服务器 git 仓库无远程 origin）

### 验证结果（生产环境，无 mock）
- 服务器端 `_is_allowed_campus_source` 测试：6 个黑名单 URL 全部返回 False，3 个允许来源 URL 全部返回 True ✓
- 服务重启后健康检查返回 `{"status": "ok"}`
- 清理了服务器上的测试用户 `u1` 和 `test_001`，`users.json` 重置为 `{}`

## 2026-09-25 — 91402 NOTEXIST 修复

**问题**：飞书 API 返回 `code=91402 NOTEXIST`

**根因**：用户多维表格挂在知识库(wiki)下，存储的 `base_token` 是 wiki node_token，直接用于 bitable API 会报错。

**修复**：
- `feishu_client.py` 新增 `resolve_app_token()` 方法
- 所有 bitable/drive API 调用前先解析 wiki node_token → obj_token
- `onboarding.py` 新增 `migrate_user_tokens()` 迁移存量用户

**影响**：所有涉及飞书 API 调用的模块
