## ISSUE-001：飞书 API 91402 NOTEXIST

**日期**：2026-09-25
**严重级别**：P0（阻塞核心功能）

### 问题
调用飞书 bitable API 时返回 `code=91402 NOTEXIST`，导致无法写入岗位数据。

### 根因
用户的多维表格挂在知识库(wiki)下。此时 URL 中的 token 段是 `node_token`，而非实际的 `obj_token`。直接用 `node_token` 调用 bitable/drive API 会返回 91402。

### 解决方案
1. `feishu_client.py` 新增 `resolve_app_token(token)` 方法：
   - 调用 `GET /open-apis/wiki/v2/spaces/get_node?token={token}`
   - 若返回 `obj_token`，使用之；若接口报错（非 wiki 节点），原样返回
2. 所有 bitable/drive/docx API 调用前先 `resolve_app_token()`
3. 新增 `migrate_user_tokens()` 迁移存量用户的 base_token

### 预防措施
- onboarding 创建多维表格后立即 `verify_bitable_access()` 验证
- 所有飞书 API 调用统一走 `resolve_app_token()` 防御

## ISSUE-002：KeyError: 'url'（文档创建）

**日期**：2026-09-24
**严重级别**：P1

### 问题
`create_doc()` 中 `data["url"]` 抛 KeyError，日报文档 URL 无法获取。

### 根因
飞书 docx v1 API 的创建文档响应中不含 `url` 字段，只有 `document_id`。

### 解决方案
手动拼接 URL：`f"https://{domain}/docx/{doc_id}"`，domain 从 `FEISHU_DOMAIN` 环境变量读取（默认 `www.feishu.cn`）。

### 预防措施
- 不假设第三方 API 响应结构，对可能缺失的字段用 `.get()` 或手动构造
- 增加 `FEISHU_DOMAIN` 配置项，支持飞书/Lark 不同域名

## ISSUE-003：Onboarding 竞态条件（创建多个多维表格）

**日期**：2026-09-23
**严重级别**：P1

### 问题
用户快速重复打开应用，飞书推送多次回调，导致为同一用户创建多个多维表格，数据写入混乱。

### 根因
`handle_feishu_callback` 中启动后台线程执行 onboarding，无并发控制。多个线程同时检查"用户不存在"后都创建了多维表格。

### 解决方案
`onboarding.py` 添加 `_onboarding_lock = threading.Lock()`：
- `onboard_user()` 中 `with _onboarding_lock:` 包裹
- 加锁后**双重检查**用户是否已存在
- 已存在则直接返回

### 预防措施
- 写操作前加锁 + 双重检查
- 未来迁移 DB 后可用唯一索引约束 `user_id`

## ISSUE-004：users.json 写权限拒绝

**日期**：2026-09-23
**严重级别**：P1

### 问题
非 root 用户运行时，`users.json` 写入报 `PermissionError`。

### 根因
文件所有者是 root，服务以 admin 用户运行，无写权限。

### 解决方案
- 统一使用 `sudo` 执行文件操作
- 确保 `data/` 目录及文件所有者与服务运行用户一致：
  ```bash
  sudo chown -R admin:admin /opt/job_assistant/data
  ```

### 预防措施
- 部署脚本中统一设置文件所有权
- systemd 服务的 `User` 与文件所有者一致

## ISSUE-005：服务不反映最新代码（缓存问题）

**日期**：2026-09-22
**严重级别**：P2

### 问题
`git pull` 后服务行为未变化，仍运行旧代码。

### 根因
- `__pycache__` 中的 `.pyc` 缓存未清理
- 服务未重启

### 解决方案
部署流程中增加：
```bash
sudo find . -name "__pycache__" -type d -exec rm -rf {} + 2>/dev/null
sudo systemctl restart job-callback
```

### 预防措施
- 标准化部署脚本（见 05-部署运维SOP.md 第 3 节）
- 每次 pull 后必须清理缓存 + 重启服务

## ISSUE-007：回调服务未校验飞书签名

**日期**：2026-09-26（发现并修复）
**严重级别**：P2
**状态**：✅ 已修复

### 问题
`callback_server.py` 未校验飞书回调的 `verification_token` 或解密 `encrypt_key`，存在伪造回调风险。

### 根因
MVP 阶段为简化开发省略了签名校验。

### 解决方案
1. 新增 `_verify_feishu_token(body)` 函数，提取 `body.token`（v1）或 `body.header.token`（v2）
2. 若配置了 `FEISHU_VERIFICATION_TOKEN`，校验请求体中的 token 是否匹配
3. 校验失败返回 403；未配置时放行（MVP 兼容）
4. `.env.example` 增加 `FEISHU_VERIFICATION_TOKEN` 配置项

### 预防措施
- 生产环境必须配置事件订阅校验
- 安全审查时检查外部回调是否有身份验证

## ISSUE-008：HashStore 无文件锁导致并发写损坏

**日期**：2026-09-26（发现并修复）
**严重级别**：P1
**状态**：✅ 已修复

### 问题
`HashStore.add()` 直接读写 hash 文件，无文件锁。并发写入可能导致文件损坏或记录丢失。

### 根因
`HashStore` 未复用 `UserStore` 的 `fcntl.flock` 机制。

### 解决方案
1. `HashStore` 新增 `_file_lock()` 上下文管理器（与 UserStore 一致）
2. `add()` 持锁后从磁盘全量重载 → 写入 → 原子保存
3. 验证：10 线程并发写入 10 个 hash，文件无损坏且全部保留

### 预防措施
- 所有 JSON 文件写操作必须持文件锁
- 新增存储类时复用 `_file_lock` 模式

## ISSUE-009：UserStore 多进程 lost-update

**日期**：2026-09-26（发现并修复）
**严重级别**：P1
**状态**：✅ 已修复

### 问题
`_reload_from_disk()` 只加载内存中不存在的用户。两个进程修改不同用户时，后保存的进程会覆盖先保存进程的修改。

### 根因
设计假设每个进程只修改自己内存中的用户，未考虑跨进程数据合并。

### 解决方案
1. `_reload_from_disk()` 改为持锁后**全量重载**（`self._users = {}` 后重新 `_load()`）
2. `upsert`/`delete` 均走全量重载 → 修改 → 保存
3. 验证：两个独立 store 实例分别修改 userA/userB，两个修改均保留

### 预防措施
- 文件存储场景下，写操作必须"持锁 + 全量重载 + 修改 + 保存"
- 用户量增长后迁移 DB，用事务替代文件锁

## ISSUE-010：飞书 API 字段格式契约错误（批量写入失败）

**日期**：2026-09-26（生产环境发现并修复）
**严重级别**：P0（阻塞核心写入功能）
**状态**：✅ 已修复

### 问题
每日任务运行时，岗位数据写入飞书多维表格连续失败，涉及 6 个不同错误码：

| 错误码 | 字段 | 现象 |
|--------|------|------|
| 1254043 | - | `RecordIdNotFound` |
| 1254068 | JD链接 | `URLFieldDetailFail` |
| 1254064 | 抓取日期 | `DatetimeFieldConvFail` |
| 1254061 | 相关性评分/难度评分 | `NumberFieldConvFail` |
| 1770001 | 日报文档块 | `invalid param` |
| - | 去重hash查询 | `'NoneType' object is not iterable` |

### 根因
6 处飞书 API 契约理解错误，均为确定性失败（每次必错）：

1. **`search_records` 端点错误**：用 `GET /records/search`，飞书将路径最后一段 `search` 当作 `record_id` 解析，返回 1254043。正确端点是 `GET /records`（列表接口）。
2. **URL 字段传空字符串**：飞书 URL 字段(type=15)只接受 `{"text","link"}` 对象，空字符串 `""` 触发 1254068。
3. **日期字段传字符串**：飞书日期字段(type=5)要求 Unix 毫秒时间戳(int)，传格式化字符串触发 1254064。
4. **数字字段类型不确定**：`相关性评分`/`难度评分` 未强制转 int，部分路径下值非纯数字触发 1254061。
5. **docx 块类型不匹配**：`block_type:3`（heading1）配了 `heading2` 内容键，飞书拒绝返回 1770001。正确：heading2 = block_type 4。
6. **API 响应 items 为 null**：`data.get("items", [])` 在 `items` 键存在但值为 `null` 时返回 `None`，`.extend(None)` 抛 `'NoneType' object is not iterable`。

### 解决方案
1. `feishu_client.search_records`：端点改为 `/records`，`data.get("items") or []` 防御 null
2. `scorer._build_url_field()`：空值返回 `None`，自动补 `https://` 前缀
3. `scorer._to_timestamp_ms()`：日期字符串转 Unix 毫秒时间戳
4. `scorer.score_job()`：`相关性评分`/`难度评分` 强制 `int()`
5. `daily_runner._create_daily_report()`：heading2 的 `block_type` 从 3 改为 4
6. `feishu_client.batch_create_records()`：新增 `_sanitize_fields()` 剔除 None 值；批量失败降级为逐条写入

### 验证（生产环境真实飞书 API）
- 多维表格主表成功写入 29 条岗位记录
- 评分字段均为有效数字（75、74、83、45、45）
- 日报文档正常生成，无 1770001 错误
- 去重查询无 NoneType 错误
- `errors: []`

### 预防措施
- 飞书字段写入值的类型必须与 schema 中 `type` 严格对应：URL→对象、日期→毫秒时间戳、数字→int
- 建表 schema 与写入转换逻辑应集中管理，避免格式不一致
- 批量写入必须有降级策略：单条失败不应导致整批丢失
- `dict.get(key, default)` 对值为 null 的情况无效，应使用 `dict.get(key) or default`
