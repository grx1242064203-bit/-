## ISSUE-001：飞书 API 91402 NOTEXIST

**日期**：2026-09-25
**严重级别**：P0（阻塞核心功能）

### 问题
调用飞书 bitable API 时返回 `code=91402 NOTEXIST`，导致无法写入岗位数据。

### 根因
用户的多维表格挂在知识库(wiki)下。此时 URL 中的 token 段是 `node_token`，而非实际的 `obj_token`。直接用 `node_token` 调用 bitable/drive API 会返回 91402。

### 解决方案
1. `feishu_client.py` 新增 `resolve_app_token(token)` 方法：
   - 调用 `GET /open-apis/wiki/v2/spaces/get_node?token={token}`
   - 若返回 `obj_token`，使用之；若接口报错（非 wiki 节点），原样返回
2. 所有 bitable/drive/docx API 调用前先 `resolve_app_token()`
3. 新增 `migrate_user_tokens()` 迁移存量用户的 base_token

### 预防措施
- onboarding 创建多维表格后立即 `verify_bitable_access()` 验证
- 所有飞书 API 调用统一走 `resolve_app_token()` 防御

## ISSUE-002：KeyError: 'url'（文档创建）

**日期**：2026-09-24
**严重级别**：P1

### 问题
`create_doc()` 中 `data["url"]` 抛 KeyError，日报文档 URL 无法获取。

### 根因
飞书 docx v1 API 的创建文档响应中不含 `url` 字段，只有 `document_id`。

### 解决方案
手动拼接 URL：`f"https://{domain}/docx/{doc_id}"`，domain 从 `FEISHU_DOMAIN` 环境变量读取（默认 `www.feishu.cn`）。

### 预防措施
- 不假设第三方 API 响应结构，对可能缺失的字段用 `.get()` 或手动构造
- 增加 `FEISHU_DOMAIN` 配置项，支持飞书/Lark 不同域名

## ISSUE-003：Onboarding 竞态条件（创建多个多维表格）

**日期**：2026-09-23
**严重级别**：P1

### 问题
用户快速重复打开应用，飞书推送多次回调，导致为同一用户创建多个多维表格，数据写入混乱。

### 根因
`handle_feishu_callback` 中启动后台线程执行 onboarding，无并发控制。多个线程同时检查"用户不存在"后都创建了多维表格。

### 解决方案
`onboarding.py` 添加 `_onboarding_lock = threading.Lock()`：
- `onboard_user()` 中 `with _onboarding_lock:` 包裹
- 加锁后**双重检查**用户是否已存在
- 已存在则直接返回

### 预防措施
- 写操作前加锁 + 双重检查
- 未来迁移 DB 后可用唯一索引约束 `user_id`

## ISSUE-004：users.json 写权限拒绝

**日期**：2026-09-23
**严重级别**：P1

### 问题
非 root 用户运行时，`users.json` 写入报 `PermissionError`。

### 根因
文件所有者是 root，服务以 admin 用户运行，无写权限。

### 解决方案
- 统一使用 `sudo` 执行文件操作
- 确保 `data/` 目录及文件所有者与服务运行用户一致：
  ```bash
  sudo chown -R admin:admin /opt/job_assistant/data
  ```

### 预防措施
- 部署脚本中统一设置文件所有权
- systemd 服务的 `User` 与文件所有者一致

## ISSUE-005：服务不反映最新代码（缓存问题）

**日期**：2026-09-22
**严重级别**：P2

### 问题
`git pull` 后服务行为未变化，仍运行旧代码。

### 根因
- `__pycache__` 中的 `.pyc` 缓存未清理
- 服务未重启

### 解决方案
部署流程中增加：
```bash
sudo find . -name "__pycache__" -type d -exec rm -rf {} + 2>/dev/null
sudo systemctl restart job-callback
```

### 预防措施
- 标准化部署脚本（见 05-部署运维SOP.md 第 3 节）
- 每次 pull 后必须清理缓存 + 重启服务

## ISSUE-007：回调服务未校验飞书签名

**日期**：2026-09-26（发现）
**严重级别**：P2（待修复）

### 问题
`callback_server.py` 未校验飞书回调的 `verification_token` 或解密 `encrypt_key`，存在伪造回调风险。

### 根因
MVP 阶段为简化开发省略了签名校验。

### 解决方案（待执行）
1. 配置 `FEISHU_VERIFICATION_TOKEN` 环境变量
2. 在 `do_POST` 中校验请求头中的 `X-Lark-Request-Token`
3. 如配置了 `FEISHU_ENCRYPT_KEY`，解密请求体

### 预防措施
- 生产环境必须配置事件订阅校验
- 安全审查时检查外部回调是否有身份验证
