## ADR-001：飞书资源由应用身份创建，再转所有权给用户

**日期**：2026-09-22
**状态**：已采纳

### 背景
飞书应用需要为每个用户创建专属多维表格。有两种方式：
1. 使用 `user_access_token`（用户身份）创建
2. 使用 `tenant_access_token`（应用身份）创建，再转移所有权给用户

### 选项
- **选项 A**：用户身份创建。需要用户授权，token 有效期短，刷新复杂
- **选项 B**：应用身份创建 + 转所有权。用户无需授权，但需应用有足够权限

### 结论
采用选项 B。

### 后果
- ✅ 避免了 `user_access_token` 刷新的复杂性
- ✅ 用户真正拥有数据（所有权转移后）
- ⚠️ 应用需申请 `drive:drive` 权限（分享 + 转所有权）
- ⚠️ 转所有权可能失败，已降级为只分享（`full_access`）

## ADR-002：WxPusher 而非微信服务号

**日期**：2026-09-22
**状态**：已调整（见 ADR-008）

### 背景
需要向用户微信推送每日日报。

### 选项
- **选项 A**：微信服务号模板消息。每月仅 4 条，不够日推
- **选项 B**：WxPusher。无推送频率限制，零资质接入

### 结论
采用选项 B。

### 后果
- ✅ 无推送频率限制
- ✅ 零审核，10 分钟接入
- ⚠️ 依赖第三方服务，需做降级（推送失败不影响飞书数据）

## ADR-003：JSON 文件存储用户数据

**日期**：2026-09-22
**状态**：已采纳（MVP 阶段）

### 背景
需要存储用户配置和岗位去重哈希。

### 选项
- **选项 A**：JSON 文件。简单，无需额外服务
- **选项 B**：SQLite。轻量，支持事务
- **选项 C**：MySQL/PostgreSQL。完整功能，但运维成本高

### 结论
采用选项 A，MVP 阶段用户量小。

### 后果
- ✅ 零运维成本
- ✅ 数据可读性强
- ⚠️ 并发控制依赖文件锁（fcntl），多进程场景有 lost-update 风险
- ⚠️ 用户量增长后需迁移 DB（数据结构已用 dataclass，迁移成本可控）

## ADR-006：飞书 API 使用 tenant_access_token 而非 user_access_token

**日期**：2026-09-22
**状态**：已采纳

### 背景
调用飞书 API 需要鉴权。

### 选项
- **选项 A**：`user_access_token`。代表用户身份，但有效期短（2 小时），刷新复杂
- **选项 B**：`tenant_access_token`。代表应用身份，有效期 2 小时，自动刷新

### 结论
采用选项 B。

### 后果
- ✅ token 管理简单（应用级别，无需每个用户单独刷新）
- ✅ 应用身份创建资源，不依赖用户 token 有效性
- ⚠️ 需要应用有足够的 API 权限

## ADR-007：关闭岗位归档到独立表

**日期**：2026-09-22
**状态**：已采纳

### 背景
岗位关闭后需要从主表移除，但保留历史记录。

### 选项
- **选项 A**：主表中标记"是否在招=否"
- **选项 B**：归档到独立的"已关闭岗位"表

采用选项 B。

- ✅ 已关闭岗位历史可查
- ⚠️ 归档操作需要 3 次 API 调用（读完整记录 → 写已关闭表 → 删主表记录）

## ADR-008：飞书为主推送渠道，WxPusher 降级为可选

**日期**：2026-09-26
**状态**：已采纳

### 背景
用户反馈 WxPusher 未收到微信推送。经核查，WxPusher 的微信公众号推送通道已被微信官方关闭，消息只能送达 WxPusher App，无法直达用户微信。

### 选项
- **选项 A**：更换其他微信推送服务（如 PushPlus、Server酱）。仍受微信政策限制，不稳定
- **选项 B**：飞书为主推送渠道，WxPusher 降级为可选辅助
- **选项 C**：完全移除微信推送，只用飞书

### 结论
采用选项 B。

### 后果
- ✅ 飞书触达率 100%（用户已安装应用）
- ✅ 飞书卡片支持富文本、按钮、链接，体验远超纯文本推送
- ✅ 保留 WxPusher 代码，用户需要时仍可绑定
- ⚠️ 依赖飞书作为唯一主推送渠道，若飞书消息受限则无备用

## ADR-009：LLM 简历解析采用 DeepSeek

**日期**：2026-09-26
**状态**：已采纳

### 背景
需要从用户简历文本中提取结构化画像（学校、学历、技能等）。

### 选项
- **选项 A**：正则/关键词提取。零成本但准确率低，无法理解语义
- **选项 B**：GPT-4o。准确率高但成本高
- **选项 C**：DeepSeek。中文支持强、成本低（约 GPT-4 的 1/10）、API 兼容 OpenAI 格式

### 结论
采用选项 C。

### 后果
- ✅ 中文简历解析准确率高
- ✅ 成本可控，适合免费用户量
- ✅ API 兼容 OpenAI 格式，后续可无缝切换
- ⚠️ 依赖第三方 API，需做降级（LLM 失败时返回空画像，用户手动填写）
- ⚠️ API Key 由运营方统一配置，用户无需提供

## ADR-010：去重 hash 基于公司+岗位标题（聚类去重）

**日期**：2026-09-26
**状态**：已采纳

### 背景
原去重 hash 包含 公司+标题+地点+JD链接，导致同一公司同一岗位在不同城市/不同 URL 被判为不同岗位，用户看到重复岗位。

### 选项
- **选项 A**：保持原 hash（公司+标题+地点+URL）。精准但有重复
- **选项 B**：仅 公司+标题（归一化）。同一公司同一岗位只显示一次
- **选项 C**：公司+标题+地点。同一岗位不同城市算不同

### 结论
采用选项 B。归一化去除括号、空白、招聘后缀。

### 后果
- ✅ 同一公司同一岗位只显示一次，用户体验更好
- ✅ 归一化处理避免"产品经理(北京)"与"产品经理"被判为不同
- ⚠️ 同一岗位不同城市只保留先入的那条（用户可能错过其他城市的同一岗位）
- ⚠️ 历史 hash 不兼容，老用户的 hash 文件需清理

## ADR-011：校招岗位采用中心化总数据库架构

**日期**：2026-09-26
**状态**：已采纳

### 背景
校招岗位具有"一次发布、多人适用"的特点。原架构中每个校招用户独立搜索采集，存在三大问题：
1. **重复采集**：N 个校招用户对同一家公司搜索 N 次，浪费搜索 API 配额
2. **数据不一致**：不同用户搜到的同一岗位可能因搜索时间不同而内容/状态不一致
3. **采集质量参差**：独立搜索的来源过滤和 AI 检视无法保证统一质量

### 选项
- **选项 A**：保持每用户独立搜索采集。简单但浪费配额、数据不一致。
- **选项 B**：中心化采集 → 总数据库 → 用户按需分发。一次采集，多人共享，统一质量。
- **选项 C**：中心化采集但不存数据库，每次实时搜索后分发。无法增量更新，无法去重。

### 结论
采用选项 B。

### 架构
```
公司来源库(campus_companies) → company_crawler(中心化采集) → job_db(总数据库, SQLite)
                                                                      │
                                                          user_matcher(规则预筛+AI评分)
                                                                      │
                                                              用户飞书多维表格
```

### 后果
- ✅ 搜索 API 配额消耗从 O(N用户 × M公司) 降为 O(M公司)
- ✅ 所有校招用户看到的岗位数据一致（同一总库）
- ✅ AI 检视统一在入库时执行，保证数据质量
- ✅ 总数据库可独立扩展（新公司发现、公告关闭复查等）
- ⚠️ 总数据库成为单点，需定期备份（已加入 backup.sh）
- ⚠️ 总数据库为空时校招用户无岗位可推，需确保首次全量采集成功
- ⚠️ SQLite 并发写限制：采集与分发需串行或加锁（采集在 8:00，分发在 9:00，时序错开）

## ADR-012：校招公司库以 2024-2026 历史发公告企业为基础盘

**日期**：2026-09-26
**状态**：已采纳

### 背景
需要构建校招公司来源库，确定采集范围。校招企业具有高延续性（往年发过公告的企业今年大概率继续发）。

### 选项
- **选项 A**：只收录各行业 TOP 50 企业。覆盖面窄，遗漏大量第二梯队企业。
- **选项 B**：收录 2024-2026 实际发过秋招/春招公告的企业（目标覆盖率 95%）。覆盖面广，延续性强。
- **选项 C**：不预设公司库，纯靠关键词搜索。无法定向采集官网，来源质量不可控。

### 结论
采用选项 B。

### 公司库构成
- **基础盘**：2024-2026 发过校招的 488 家企业（覆盖 16 个行业）
- **增量补充**：核心公众号/高校 CDC 发现的今年新招聘公司（AI 校验后补入）

### 后果
- ✅ 覆盖面广，488 家企业基本覆盖 2024-2026 校招主力企业
- ✅ 延续性强，往年发公告的企业今年大概率继续
- ⚠️ 需持续维护：每年校招季结束后复盘，补充新企业、移除停招企业
- ⚠️ 官网域名（career_domain）和公众号（wechat_account）需逐步填充，当前仅 32 家有 career_domain
