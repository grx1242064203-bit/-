# 简历评估 & 岗位匹配 — AI 产品经理设计方案

## 一、系统现状 & 模型边界

### 1.1 系统架构（两个 LLM 模块 + 一个规则引擎）

```
用户上传简历(PDF)
    ↓
[LLM 模块 A] 简历解析 (resume_parser.py, DeepSeek-chat)
    输入: 简历文本
    输出: structured_keywords (30-50个结构化关键词, 含推断补全)
          fit_directions (3-6个适配岗位方向, 带权重+依据)
    ↓
用户画像 UserProfile (models.py)
    degree/major/school + keywords + fit_directions + 偏好
    ↓
[规则引擎] 岗位评分 (scorer.py, 非 LLM)
    输入: UserProfile × 单个岗位 Dict
    输出: 0-100 分 + 8 维分项 + 推荐等级(强烈推荐/推荐/可申请/不建议)
    ↓
Top-N 排序 → 推荐给用户
```

### 1.2 模型边界定义

| 能力 | 边界 | 设计依据 |
|---|---|---|
| **简历解析能做的** | 提取硬技能/学历/学校/专业/证书；推断技术栈底层语言；标注适配岗位方向(受岗位树受控) | DeepSeek-chat 对结构化信息抽取能力稳定 |
| **简历解析不能做的** | 评估软技能(领导力/沟通)；判断项目含金量；评估学校档次 | LLM 软技能提取不稳定(v1 已移除 soft_skill 维度)；项目价值判断需行业知识 |
| **评分引擎能做的** | 硬门槛过滤(学历/专业/城市)；方向对齐(role gate)；竞争力档位匹配；硬技能命中 | 规则引擎确定性高，可解释 |
| **评分引擎不能做的** | 判断用户"真实意愿"偏好(可能想转行)；评估岗位发展潜力；理解简历项目的深度 | 规则无法建模主观意图和长期价值 |
| **整体系统边界** | 给出"方向对口+硬门槛达标+竞争力匹配"的岗位排序，不替代用户最终决策 | PM 定位: 推荐而非决策 |

### 1.3 当前 8 维评分体系

| 维度 | 权重 | 含义 | 信号来源 |
|---|---|---|---|
| competitiveness | 0.20 | 候选人档位 vs 岗位档位对齐 | 学校+学历+技能推算 candidate_tier vs 公司行业地位 company_tier |
| role | 0.15 | 求职方向核心偏好 | fit_directions 的 cat_key/sub_key 与岗位 category/subcategory 匹配 |
| hard_skill | 0.15 | 真实硬技能命中 | structured_keywords 中 category=hard_skill 的交集 |
| education | 0.15 | 学历硬门槛 | profile.degree vs job.min_education (不达标直接 0 分) |
| major | 0.10 | 专业匹配 | profile.major vs job.major_required (含专业大类映射) |
| skill | 0.10 | 综合技能覆盖 | 全部关键词 Jaccard 相似度 |
| company_preference | 0.10 | 目标公司偏好 | target_companies/industries 匹配 |
| city | 0.05 | 地域偏好 | target_cities vs job.city |

**特殊机制**: role 维度 < 40 分时触发方向硬门槛，总分上限压到 45 分（"不建议"档），防止方向错配靠泛技能刷分。

## 二、核心问题：匹配评测为什么比拆岗难？

### 2.1 拆岗 vs 匹配的本质区别

| 维度 | 拆岗评测 | 匹配评测 |
|---|---|---|
| Ground truth | 客观存在(公告里实际有几个岗位) | **主观的**(用户觉得好才是好) |
| 评测方式 | 人工标注正确答案 | 需要用户反馈或专家判断 |
| 样本量 | 25 条够(每条独立) | 需要多个用户 × 多个岗位的组合 |
| 迭代周期 | Prompt 改完秒跑回归 | 需要 A/B 测试观察用户行为 |

### 2.2 PM 的解法：三层评测体系

| 层级 | 方式 | 样本 | 指标 | 用途 |
|---|---|---|---|---|
| **Layer 1: 离线评测** | 专家标注 relevance | 3 用户 × 50 岗位 = 150 对 | Precision@10, NDCG@10, Recall@30 | 快速迭代验证 |
| **Layer 2: 在线 A/B** | 用户行为隐式反馈 | 20 用户 × 2 周 | 点击率, 申请率, 忽略率 | 验证线上效果 |
| **Layer 3: 满意度** | 用户显式反馈 | 20 用户 | NPS, "推荐命中率" | 长期质量监控 |

## 三、离线评测设计（Layer 1 — 可立即执行）

### 3.1 评测集构建

**用户侧**: 选 3 个真实用户画像（不同背景）
- 用户 A: 林叙言（嵌入式 AI 开发，硕士，西安交大）— 已有 test_scorer_linxuyan.py
- 用户 B: 待选（商科/金融背景）
- 用户 C: 待选（计算机/后端开发背景）

**岗位侧**: 从 6303 个岗位中抽取 50 个，分层:
- 15 个: 方向高度对口（fit_directions 前 2 名对应的 subcategory）
- 15 个: 方向部分对口（fit_directions 第 3-6 名）
- 10 个: 方向不对口但技能有交集（如嵌入式用户 × 后端开发岗）
- 10 个: 完全不对口（如嵌入式用户 × 财务/审计岗）

**标注**: 对每个 (用户, 岗位) 对，人工标注 relevance:
- **relevant(2)**: 方向对口+硬门槛达标+会投递
- **partial(1)**: 方向弱相关或硬门槛边缘
- **irrelevant(0)**: 方向错配或硬门槛不达标

### 3.2 核心指标

| 指标 | 公式 | 目标 | 说明 |
|---|---|---|---|
| **Precision@10** | Top-10 中 relevant 数 / 10 | > 70% | 用户看到的前 10 个岗位至少 7 个对口 |
| **NDCG@10** | DCG@10 / IDCG@10 | > 0.65 | 排序质量(relevant 排前面) |
| **Recall@30** | Top-30 中 relevant 数 / 总 relevant 数 | > 80% | 不漏推好岗位 |
| **Hard Gate Accuracy** | 硬门槛违规岗位出现在 Top-30 的比例 | < 5% | 学历/专业不达标的岗位不应出现 |
| **Direction Mismatch Rate** | Top-10 中方向错配(role < 40)的比例 | < 10% | 方向硬门槛有效性 |

### 3.3 评测脚本设计

```python
# eval/matching_eval.py
"""
输入: evalset_matching.json
  - users: [UserProfile A/B/C]
  - jobs: [50 个岗位 Dict]
  - judgments: [{user_id, job_id, relevance: 0/1/2}]

输出:
  - Precision@10, NDCG@10, Recall@30
  - 每用户的 Top-10 列表 + relevance 标注对比
  - bad case: Top-10 中的错配岗位
"""
```

## 四、Bad Case 分类体系

### 4.1 五类匹配 Bad Case

| 类型 | 定义 | 根因 | 修复方向 |
|---|---|---|---|
| **F1: 方向错配** | Top-10 出现 role < 40 的岗位 | role gate 未触发或阈值不当 | 调整 ROLE_GATE_THRESHOLD |
| **F2: 硬门槛失效** | 学历/专业不达标的岗位进入 Top-30 | education 维度评分逻辑 bug | 硬门槛直接置 0 + 总分上限 |
| **F3: 泛技能刷分** | 方向不对但靠通用技能(skill 维度)挤进 Top-10 | skill 与 hard_skill 双重计分 | 删除 skill 维度(维度缩减) |
| **F4: 竞争力错配** | 保底候选人 × 顶档岗位被高分推荐 | competitiveness 权重或档位算法不准 | 调整 candidate_tier 计算 |
| **F5: 冷启动平庸** | 简历稀疏 → 所有岗位 60 分(无区分度) | 缺少足够的 structured_keywords | 强化简历解析推断补全 |

### 4.2 Bad Case 池示例（基于林叙言画像）

```
用户: 林叙言 (嵌入式AI, 硕士, 西安交大)
fit_directions: 边缘AI(0.95) > 嵌入式软件(0.90) > ML算法(0.70) > CV(0.60) > 通信(0.40)

预期 Top-5:
  1. 嵌入式软件工程师 (role=95, hard_skill=85) → score ~85 "强烈推荐"
  2. AI算法工程师-边缘部署 (role=90, hard_skill=75) → score ~80 "强烈推荐"
  3. 机器学习算法工程师 (role=70, hard_skill=70) → score ~68 "推荐"
  4. CV算法工程师 (role=60, hard_skill=55) → score ~58 "推荐"
  5. 后端开发工程师 (role=40, hard_skill=40) → score ~45 "可申请" (role gate 触发)

Bad Case 候选:
  F1: 财务会计岗出现在 Top-10 → role 应为 0, 但 skill=20 拉高总分?
  F3: 前端开发岗靠 Python+SQL 命中 skill 维度挤进 Top-10?
  F4: 华为天才少年岗(顶档)推荐给保底候选人?
```

## 五、维度缩减 A/B 测试设计

### 5.1 假设

> **H1**: 删除 skill(0.10) 和 company_preference(0.10) 后，Top-10 方向对口率提升，且 NDCG@10 不降。

**依据**:
- skill 维度是全关键词 Jaccard，与 hard_skill(精确硬技能交集) 高度重叠 → 双重计分导致泛技能刷分(F3)
- company_preference 在 20 个用户中仅 2-3 个填写了目标公司 → 信号稀疏，对 85% 用户无区分度

### 5.2 实验设计

| 组 | 维度 | 权重分配 | 样本 |
|---|---|---|---|
| **对照组 v1** | 8 维(现状) | skill=0.10, company_pref=0.10 保留 | 3 用户 × 50 岗位 |
| **实验组 v2** | 6 维(缩减) | 删除 skill+company_pref，0.20 重分配给 competitiveness(+0.10) + hard_skill(+0.05) + role(+0.05) | 同上 |

**v2 权重方案**:
```
competitiveness: 0.20 → 0.30  (+0.10, 吸收 company_preference 的公司对齐信号)
hard_skill:      0.15 → 0.20  (+0.05, 吸收 skill 的精确技能命中信号)
role:            0.15 → 0.20  (+0.05, 强化方向对齐权重)
education:       0.15 → 0.15  (不变)
major:           0.10 → 0.10  (不变)
city:            0.05 → 0.05  (不变, 但可考虑提升)
```
总 = 1.00

### 5.3 评估指标 & 判定标准

| 指标 | v1 基线 | v2 目标 | 判定 |
|---|---|---|---|
| Precision@10 | 待测 | > v1 + 5% | v2 胜出 |
| NDCG@10 | 待测 | ≥ v1 (不退化) | v2 不输 |
| F3 泛技能刷分率 | 待测 | < v1 的 50% | v2 胜出 |
| F1 方向错配率 | 待测 | < v1 | v2 胜出 |

**判定规则**: 4 个指标中 ≥ 3 个达标 → v2 上线

### 5.4 执行步骤

```
Step 1: 构建 evalset_matching.json (3 用户 × 50 岗位 + relevance 标注)
Step 2: 跑 v1(8维) → 记录 Precision@10 / NDCG@10 / F3率 / F1率
Step 3: 修改 scorer.py DIMENSION_WEIGHTS 为 v2(6维)
Step 4: 跑 v2(6维) → 记录同样指标
Step 5: 对比报告 → 判定是否上线
```

## 六、回流机制设计

```
线上: 用户查看推荐列表
    ↓
隐式反馈: 点击/申请/忽略 → 按 job_id + user_id 记录
    ↓
每周聚合:
  - 点击未申请的岗位 → "看了但不投" → 可能 over-recommend
  - 未点击但排名靠前的岗位 → "没看但排前面" → 可能 false positive
  - 用户主动搜索但未在推荐中的岗位 → "漏推" → false negative
    ↓
Bad Case 池(按 F1-F5 分类):
  - 每周抽样 20 条(用户, 岗位)对 → 人工标注 relevance
  - 与系统评分对比 → 不一致的进 bad case 池
    ↓
迭代:
  - F1 方向错配 → 调整 ROLE_GATE_THRESHOLD
  - F3 泛技能刷分 → 维度权重调整(本方案)
  - F4 竞争力错配 → 优化 candidate_tier 计算
  - F5 冷启动 → 优化简历解析推断补全
    ↓
回归测试: 25 条拆岗评测集 + 150 对匹配评测集 → 确保无退化 → 上线
```

**回流 SLA**:
- 隐式反馈 → 每周聚合: 1 天
- Bad case 抽样标注: 2 天
- 权重/规则调整 + 回归: 2 天
- 总计: 5 天/迭代周期

## 七、面试追问 & 回答要点

### Q1: "匹配的 ground truth 是主观的，你怎么评测？"
> 三层：离线用专家标注 relevance(3 用户 × 50 岗位 = 150 对)，在线用隐式反馈(点击率/申请率)，长期用 NPS。离线阶段 Fast iteration，在线阶段验证真实效果。

### Q2: "为什么删 skill 和 company_preference 两个维度？"
> skill 是全关键词 Jaccard，和 hard_skill(精确硬技能交集) 高度重叠，导致"懂一点 Python 的财务专业"靠泛技能刷分挤进嵌入式岗 Top-10。company_preference 在 20 个用户中只有 2-3 个填了目标公司，信号稀疏。A/B 测试验证删除后 Precision@10 提升 5%+ 且 NDCG 不退化才上线。

### Q3: "方向硬门槛(role gate)怎么设计的？"
> role 维度 < 40 分时，总分上限压到 45 分(不建议档)。解决"方向错配但靠泛技能/字符级假命中刷分挤进 Top"的问题。第一性原理：方向是用户最核心偏好，方向不对的岗位对用户无价值。

### Q4: "竞争力档位怎么算的？"
> candidate_tier 从学校+学历+技能综合推算(顶/中/保底)，company_tier 从公司行业地位+规模+竞争度判断。alignment 评分两者对齐度。权重 0.20(最大) → v2 提升到 0.30，因为竞争力对齐是用户感知最强的信号。

### Q5: "冷启动怎么办？"
> 简历解析的推断补全规则(如 PyTorch → 补 Python + 机器学习)能让稀疏简历从 10 个关键词扩展到 30-50 个。但极端冷启动(简历极短)所有维度都低，总分 40-50 区间区分度差。解决方案：加 context(用户主动选 3 个意向方向) + 降权硬技能(信号弱时不过度惩罚)。
