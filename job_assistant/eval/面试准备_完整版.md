# Offer搭子 — 面试准备（完整版）

> 涵盖拆岗 + 简历匹配两个 LLM 模块。面试时以拆岗为主线（数据最全），匹配为辅线（展示 A/B 测试能力）。

---

## 一、数据情况

### 1.1 数据规模

| 维度 | 数值 | 来源 |
|---|---|---|
| 招聘公告总量 | 6303 条 | jobs.db announcements 表 |
| LLM 拆岗结果 | 全量缓存（content_hash 索引） | data/llm_cache/ |
| 拆岗评测集 | 25 条（5 分层抽样） | evalset_positions.json |
| 匹配评测集 | 53 岗位 × 1 用户 | evalset_matching.json |
| 真实付费用户 | 20 人 | 产品 V1 飞书应用 |
| 模型 | deepseek-chat（67B） | llm_client.py |
| 单次拆岗成本 | ~¥0.04/条 | DeepSeek API 定价 |

### 1.2 拆岗评测集分层设计（25 条）

| 分层 | 样本数 | 特征 | 典型样本 |
|---|---|---|---|
| A_single 单岗 | 5 | 公告只含 1 个岗位 | OC&C 助理咨询顾问 |
| B_multi 多岗 | 10 | 标题/正文含 2-10 个岗位 | 禾迈 8 岗、毕马威 7 岗 |
| C_heavy 重型 | 5 | 10+ 岗位或大类细分 | 昆仑芯 12 岗、节卡 16 岗 |
| D_outlier 异常 | 2 | 超长/合并格式 | 岚图 39 岗、禾赛 31 岗 |
| E_mt 管培 | 3 | 管培生/培训生类 | 仕佳光子、南粤银行 |

**分层依据**：按 LLM 拆出岗位数分布 + bad case 类型分布，确保各类边界场景覆盖。

### 1.3 匹配评测集分层设计（53 岗位）

| 分层 | 样本数 | 特征 | 标注方式 |
|---|---|---|---|
| 强相关(GT=2) | 30 | 方向在 fit_directions 内（edge_ai/embedded_sw/ml/cv/communication） | job_subcategory 匹配 |
| 边界(GT=1) | 10 | 方向不对但技能有 ≥1 交集（后端/数据/测试/FPGA/IC/大模型） | 技能交集判断 |
| 不对口(GT=0) | 13 | 方向不对且技能无交集（财务/市场/HR/销售） | job_subcategory 不匹配 |

**标注策略**：不做细粒度评分（分不清"ML算法"和"AI算法"的区别），只做二分+边界标注。用 job_subcategory 是否在 fit_directions 作为 ground truth，技能交集≥1 为边界样本。这是诚实面对"人分不清细分岗位"的解法。

### 1.4 数据流

```
飞书源表 → 爬虫抓取正文 → LLM 拆岗(DeepSeek-chat) → 缓存(JSON)
                                          ↓
                                    评测集(25条) → 人工标注 → 基线报告
                                          ↓
                                    Prompt v2 迭代 → 回归测试 → 对比报告

用户简历 → LLM 解析(DeepSeek-chat) → 结构化画像(fit_directions+硬技能)
                                          ↓
                                    匹配评测集(53岗位) → scorer 8维打分 → v1基线
                                          ↓
                                    6维缩减 A/B → v2对比 → 决策上线
```

## 三、测评设计

### 3.1 拆岗：双层评测体系

| 层级 | 方式 | 样本量 | 指标 | 用途 |
|---|---|---|---|---|
| Layer 1 | 程序硬指标 | 全量(6303) | JSON schema 合法率、字段填充率、岗位树命中率 | 线上监控, 秒级 |
| Layer 2 | 人工标注 | 25 条 | 拆岗准确率、漏拆率、幻觉率、归类准确率、字段错误分布 | 基线建立 + 迭代验证 |

**为什么双层**：Layer 1 能自动化但只能抓"格式错"（JSON 损坏/字段缺失），抓不了"语义错"（漏拆/幻觉/归类错误）。Layer 2 人工标注抓语义错，但成本高只能抽样。两者互补。

### 3.2 拆岗：五维评测指标

| 维度 | 指标 | v1 基线 | v2 最终 | 说明 |
|---|---|---|---|---|
| 拆岗数量 | split_accuracy | 76.0% | 80.0% | 19/25 → 20/25 条正确 |
| 岗位归类 | category_accuracy | 96.8% | 96.8% | 209/216 个正确 |
| 字段质量 | city 填充率 | 85.2% | 100.0% | 强制填充规则 |
| 整体评分 | avg_score | 3.48/5 | - | 6 条满分, 1 条 1 分 |
| Bad case | clean_rate | 64.0% | - | 9/25 无任何问题 |

### 3.3 匹配：三层评测体系

| 层级 | 方式 | 指标 | 用途 |
|---|---|---|---|
| 离线标注 | 53 岗位 × 1 用户 | Precision@10 / NDCG@10 / Recall@30 | A/B 测试对比 |
| 在线 A/B | 真实用户分流 | 点击率 / 申请率 / 满意度 | 线上验证 |
| 隐式反馈 | 用户行为日志 | 忽略率 / 收藏率 / 申请转化 | bad case 回流 |

**离线指标定义**：
- **Precision@10**：Top-10 推荐中强相关岗位占比（目标 >70%）
- **NDCG@10**：Top-10 排序质量（考虑位置折扣，目标 >0.65）
- **Recall@30**：Top-30 覆盖了多少比例的相关岗位（目标 >80%）
- **Hard Gate 违规率**：Top-30 中学历不达标占比（目标 <5%）
- **方向错配率**：Top-10 中 role < 40 分的占比（目标 <10%）

### 3.4 匹配：v1 vs v2 对比

| 指标 | v1(8维) | v2(6维) | 变化 |
|---|---|---|---|
| Precision@10 | 100% | 100% | → |
| NDCG@10 | 1.000 | 1.000 | → |
| **Recall@30** | **76.7%** | **80.0%** | **↑3.3%** |
| F3 泛技能刷分 | 0 | 0 | → |

## 四、Bad Case 和回流机制

### 4.1 拆岗：v1 基线 Bad Case 分布

| 类型 | 数量 | 占比 | 典型样本 |
|---|---|---|---|
| none (无问题) | 9 | 36% | - |
| wrong_field (字段错误) | 8 | 32% | city 为空(最普遍) |
| missed (漏拆) | 4 | 16% | 标题连续岗位名未拆开 |
| hallucinated (幻觉/误拆) | 2 | 8% | 幻觉实习生岗位 |
| wrong_category (归类错误) | 2 | 8% | 品牌助理归为内容创意 |

### 4.2 拆岗：三大核心 Bad Case 根因

**Bad Case 1: 标题连续岗位名漏拆（4 条, 最严重）**
- 现象：标题含多个岗位名无分隔符，LLM 只取最后一个
- 样本：EVAL-001 澜起科技 "模拟设计数字设计数字验证产品工程师" → 只取"产品工程师"
- 根因：DeepSeek-chat 缺乏中文岗位名边界识别，遇到连续中文名时倾向取末尾
- 影响：漏拆 27 个岗位，漏拆率 11.8%
- 修复尝试：0b 规则写 3 个 few-shot 示例，但模型未执行 → 记为已知问题

**Bad Case 2: city 字段大面积缺失（17 个错误）**
- 现象：多岗位公告中 city 字段为空
- 样本：EVAL-011 阿里健康 9 个岗位 city 全空（应填杭州）
- 根因：LLM 在正文较长时容易遗漏元数据字段
- 修复：Prompt 加 city 强制填充规则 → 85.2%→100% ✅

**Bad Case 3: 非招聘公告强行拆岗（2 条）**
- 现象：培训回顾/活动通知被当招聘公告处理
- 样本：EVAL-024 仕佳光子管培生入职培训回顾 → 仍拆出岗位
- 根因：缺少"非招聘公告"的拒答机制
- 修复：0a 拒答规则 → EVAL-012 误伤 → 细化拒答条件 → 修复 ✅

### 4.3 匹配：五类 Bad Case

| 类型 | 根因 | 修复策略 |
|---|---|---|
| F1 方向错配 | role gate 阈值过松 | 调 ROLE_GATE_THRESHOLD |
| F2 硬门槛失效 | education 逻辑缺陷 | 硬门槛置 0 + 总分上限 |
| **F3 泛技能刷分** | skill 与 hard_skill 重叠 | **维度缩减(6维)** |
| F4 竞争力错配 | tier 计算不准 | 优化 candidate_tier |
| F5 冷启动平庸 | 简历稀疏 | 强化推断补全 |

**F3 是维度缩减的直接动因**：skill 维度（泛技能 Jaccard）和 hard_skill 维度（精确技能匹配）信号高度重叠，skill 维度反而让"方向不对但技能有交集"的边界样本刷高分。删除 skill 后，competitiveness 权重从 0.20→0.30 吸收了信号，Recall@30 +3.3%。

### 4.4 回流机制设计

```
拆岗模块回流:
  线上 LLM 结果 → content_hash 缓存(JSON)
          ↓
  每月抽样 50 条 → LLM-as-Judge 自动标注 + 人工审核
          ↓
  Bad Case 池(按错误类型分类):
    - missed: 漏拆 → Prompt 补充拆分规则
    - hallucinated: 幻觉 → 强化源文本校验
    - wrong_field: 字段缺失 → Prompt 强制填充规则
    - wrong_category: 归类错误 → 岗位树补全别名
          ↓
  迭代 Prompt v(n) → 回归测试(25 条) → 验证无退化 → 上线

匹配模块回流:
  线上推荐结果 → 用户隐式反馈(点击/申请/忽略)
          ↓
  每周聚合 → 按反馈类型分类:
    - 高分但忽略 → F3 泛技能刷分嫌疑
    - 低分但申请 → F1 方向错配或 F4 竞争力错配
    - 申请但未通过 → F2 硬门槛失效
          ↓
  Bad Case 池 → 维度权重调整 → 回归(53 岗位) → 上线
```

**回流 SLA**：
- 发现 → 归类：1 天
- 归类 → Prompt/权重改动：2 天
- 改动 → 回归验证：1 天
- 验证通过 → 上线：当天

## 六、关键问题设计及效果

### Q1: "你的拆岗评测集只有 25 条，样本量够吗？"

> 25 条是分层抽样，覆盖了 5 种边界场景（单岗/多岗/重型/异常/管培）。基线阶段用人工标注保证 ground truth 可信；迭代阶段用同一批 25 条做回归，确保对比有效性。线上监控阶段会引入 LLM-as-Judge 扩展到 100+ 样本自动评测。

### Q2: "为什么不用 LLM-as-Judge 替代人工标注？"

> 人工标注是建立可信基线，LLM-as-Judge 是规模化为线上监控服务的。先用 25 条人工标注校准 LLM judge 的一致性（吻合度 >80% 才敢用），再用 LLM judge 处理 100+ 条线上样本。两者不是替代关系，是递进关系。

### Q3: "标题连续岗位拆分为什么没解决？"

> DeepSeek-chat（67B）在中文无分隔符岗位名边界识别上能力不足。0b 规则写了 3 个 few-shot 示例但模型未执行。解决方案有两个：(1) 换用 DeepSeek-reasoner(R1) 利用思维链做边界推理 (2) 前置分词预处理，用岗位名结尾词词典先做粗切分再喂给 LLM。受限于 API 成本选择了记录为已知问题。这是模型边界的真实体现——不是所有问题都能靠 Prompt 解决。

### Q4: "幻觉数为什么从 3 涨到 11？"

> city 强制填充规则可能导致 LLM 在填充更多字段时"顺手"生成更多推测性内容。这是 Prompt 工程的权衡：提高字段填充率可能带来幻觉副作用。需要下一步用 _validate_positions 的源文本校验来过滤新增幻觉。诚实说，这是一个 trade-off，不是所有优化都是正收益。

### Q5: "模型边界怎么定义的？"

> 三层定义：
> 1. **岗位树受控词表** — 1853 title 挖掘，job_category/subcategory 只能选树内词
> 2. **源文本校验** — 岗位名必须出现在 title+content 中，过滤幻觉
> 3. **Prompt 铁律** — "只提取明确出现的岗位，严禁编造"

### Q6: "匹配评分的 8 维怎么设计的？为什么不是 5 维或 10 维？"

> 从 HR 真实筛选逻辑反推：硬门槛（学历/专业/城市）+ 方向对齐（role）+ 竞争力（competitiveness）+ 技能匹配（hard_skill/skill）+ 偏好（company_preference）。最初是 10 维，删了 soft_skill（主观难量化、LLM 提取不稳定）和 cert（与硬技能重叠），收敛到 8 维。后来 A/B 测试又发现 skill 和 company_preference 信号重叠，缩减到 6 维。

### Q7: "维度缩减为什么删 skill 而不是删 hard_skill？"

> skill 是泛技能 Jaccard 相似度（含"机器学习""深度学习"这类泛词），hard_skill 是精确技能匹配（Python/C++/PyTorch）。泛词容易让"方向不对但技能有交集"的边界样本刷高分（F3）。删 skill 保留 hard_skill，让信号更精确。

### Q8: "评测集一开始区分度不够，你怎么发现的？"

> v1 跑完发现 Precision@10=100%、NDCG@10=1.0，所有指标满分。这说明不是 scorer 太好，而是评测集太简单——30 个强相关 vs 13 个不对口，差距过大。我补充了 15 个边界样本（技能有 ≥1 交集但方向不对的岗位），重新跑后 Recall@30 从"无法区分"变成 76.7% vs 80% 可区分。这个发现本身就是评测设计的迭代——评测集本身也需要迭代。

### Q9: "role gate 的阈值 40 分怎么定的？"

> 40 分是 role 维度满分 100 的 40%。fit_directions 权重≥0.4 的方向（edge_ai 0.95、embedded_sw 0.90、ml 0.70、cv 0.60）对应的岗位 role 分≥40，不触发硬门槛。权重 0.4 的 communication 方向刚好在边界。低于 40 说明用户的核心方向不包含该岗位子类，靠技能刷分进来的应该被压低。阈值是可调参数，线上数据积累后可用 ROC 曲线优化。

### Q10: "bad case 怎么回流的？"

> 拆岗：线上 LLM 结果按 content_hash 缓存。每月抽样 50 条，用 LLM-as-Judge 自动标注 + 人工审核，按错误类型归入 bad case 池。每类 bad case 对应 Prompt 改动策略，改完跑 25 条回归确保无退化后上线。SLA：发现到上线 4 天。
>
> 匹配：线上推荐结果按用户隐式反馈（点击/申请/忽略）回流。高分但忽略→F3 嫌疑，低分但申请→F1 嫌疑。每周聚合，按反馈类型归入 bad case 池，调维度权重后跑 53 岗位回归。SLA：发现到上线 5 天。
