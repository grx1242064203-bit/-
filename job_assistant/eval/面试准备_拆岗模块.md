# Offer搭子 — LLM 拆岗模块面试准备

## 一、数据情况

### 1.1 数据规模
- 公告库：6303 条真实招聘公告（来自飞书秋招源表，经微信爬虫抓取正文）
- LLM 缓存结果：data/llm_cache/ 下按 content_hash 存储的 JSON 文件
- 评测集：25 条（5 分层抽样），人工标注 ground truth

### 1.2 评测集分层设计（25 条）

| 分层 | 样本数 | 特征 | 典型样本 |
|---|---|---|---|
| A_single 单岗 | 5 | 公告只含1个岗位 | OC&C助理咨询顾问 |
| B_multi 多岗 | 10 | 标题/正文含2-10个岗位 | 禾迈8岗、毕马威7岗 |
| C_heavy 重型 | 5 | 10+岗位或大类细分 | 昆仑芯12岗、圣邦14岗、海信18岗、节卡16岗 |
| D_outlier 异常 | 2 | 超长/合并格式 | 岚图39岗、禾赛31岗 |
| E_mt 管培 | 3 | 管培生/培训生类 | 仕佳光子、南粤银行、普源精电 |

**分层依据**：按 LLM 拆出岗位数分布 + bad case 类型分布，确保各类边界场景覆盖。

### 1.3 数据流

```
飞书源表 → 爬虫抓取正文 → LLM 拆岗(DeepSeek-chat) → 缓存(JSON by content_hash)
                                          ↓
                                    评测集(25条抽样) → 人工标注 → 基线报告
                                          ↓
                                    Prompt v2 迭代 → 回归测试 → 对比报告
```

## 三、测评设计

| 层级 | 方式 | 样本量 | 指标 | 用途 |
|---|---|---|---|---|
| Layer 1 | 程序硬指标 | 全量 | JSON schema 合法率、字段填充率、岗位树命中率 | 线上监控, 秒级 |
| Layer 2 | 人工标注 | 25 条 | 拆岗准确率、漏拆率、幻觉率、归类准确率、字段错误分布 | 基线建立 + 迭代验证 |

### 3.2 五维评测指标

| 维度 | 指标 | v1 基线 | 说明 |
|---|---|---|---|
| 拆岗数量 | split_accuracy | 76.0% | 19/25 条拆岗数量正确 |
| 岗位归类 | category_accuracy | 96.8% | 209/216 个归类正确 |
| 字段质量 | field_errors | 22个 | city 17 + education 5 |
| 整体评分 | avg_score | 3.48/5 | 6条满分, 1条1分 |
| Bad case | clean_rate | 64.0% | 9/25 无任何问题 |

### 3.3 评测集标注 schema

```json
{
  "correct_position_count": 4,          // 公告实际岗位数
  "split_verdict": "under_split",        // correct/under_split/over_split
  "missed_positions": ["模拟设计"],      // 漏拆的岗位名
  "hallucinated_positions": [],          // 幻觉的岗位名
  "category_errors": [],                 // 归类错误
  "field_errors": [{"field": "city"}],   // 字段错误
  "overall_score": 1,                    // 1-5 分整体评分
  "bad_case_type": "missed",            // bad case 分类
  "notes": "根因分析"                    // 归因
}
```

## 四、Bad Case 和回流机制

### 4.1 v1 基线 Bad Case 分布

| 类型 | 数量 | 占比 | 典型样本 |
|---|---|---|---|
| none (无问题) | 9 | 36% | EVAL-003/005/007/015/017/019 |
| wrong_field (字段错误) | 8 | 32% | city 为空(最普遍) |
| missed (漏拆) | 4 | 16% | 标题连续岗位名未拆开 |
| hallucinated (幻觉/误拆) | 2 | 8% | 幻觉实习生岗位 |
| wrong_category (归类错误) | 2 | 8% | 品牌助理归为内容创意 |

### 4.2 三大核心 Bad Case 根因

#### Bad Case 1: 标题连续岗位名漏拆（4 条, 最严重）
- **现象**: 标题含多个岗位名无分隔符, LLM 只取最后一个
- **样本**: EVAL-001 澜起科技 "模拟设计数字设计数字验证产品工程师" → 只取"产品工程师"
- **根因**: DeepSeek-chat 缺乏中文岗位名边界识别, 遇到连续中文名时倾向取末尾
- **影响**: 漏拆 27 个岗位, 漏拆率 11.8%

#### Bad Case 2: city 字段大面积缺失（17 个错误）
- **现象**: 多岗位公告中 city 字段为空
- **样本**: EVAL-011 阿里健康 9 个岗位 city 全空(应填杭州)
- **根因**: LLM 在正文较长时容易遗漏元数据字段
- **影响**: city 填充率仅 85.2%

#### Bad Case 3: 非招聘公告强行拆岗（2 条）
- **现象**: 培训回顾/活动通知被当招聘公告处理
- **样本**: EVAL-024 仕佳光子管培生入职培训回顾 → 仍拆出岗位
- **根因**: 缺少"非招聘公告"的拒答机制

### 4.3 回流机制设计

```
线上 LLM 拆岗结果 → content_hash 缓存(JSON)
        ↓
定期抽样(每月 50 条) → 人工/LLM-as-Judge 标注
        ↓
Bad Case 池(按错误类型分类)
  - missed: 漏拆样本 → Prompt 补充拆分规则
  - hallucinated: 幻觉样本 → 强化源文本校验
  - wrong_field: 字段缺失 → Prompt 强制填充规则
  - wrong_category: 归类错误 → 岗位树补全别名
        ↓
迭代 Prompt v(n) → 回归测试(25 条) → 验证无退化 → 上线
```

**回流 SLA**:
- 发现 → 归类: 1 天
- 归类 → Prompt 改动: 2 天
- Prompt 改动 → 回归验证: 1 天
- 验证通过 → 上线: 当天

## 六、面试可能追问 & 回答要点

### Q1: "你的评测集只有 25 条, 样本量够吗?"
> 25 条是分层抽样, 覆盖了 5 种边界场景(单岗/多岗/重型/异常/管培)。基线阶段用人工标注保证 ground truth 可信; 迭代阶段用同一批 25 条做回归, 确保对比有效性。线上监控阶段会引入 LLM-as-Judge 扩展到 100+ 样本自动评测。

### Q2: "为什么不用 LLM-as-Judge 替代人工标注?"
> 人工标注是建立可信基线, LLM-as-Judge 是规模化为线上监控服务的。先用 25 条人工标注校准 LLM judge 的一致性(吻合度 >80% 才敢用), 再用 LLM judge 处理 100+ 条线上样本。

### Q3: "标题连续岗位拆分为什么没解决?"
> DeepSeek-chat(67B) 在中文无分隔符岗位名边界识别上能力不足。0b 规则写了 3 个 few-shot 示例但模型未执行。解决方案有两个: (1) 换用 DeepSeek-reasoner(R1) 利用思维链做边界推理 (2) 前置分词预处理, 用岗位名结尾词词典先做粗切分再喂给 LLM。受限于 API 成本选择了记录为已知问题。

### Q4: "幻觉数为什么从 3 涨到 11?"
> city 强制填充规则可能导致 LLM 在填充更多字段时"顺手"生成更多推测性内容。这是 Prompt 工程的权衡: 提高字段填充率可能带来幻觉副作用。需要下一步用 _validate_positions 的源文本校验来过滤新增幻觉。

### Q5: "模型边界怎么定义的?"
> 三层定义: (1) 岗位树受控词表 — 1853 title 挖掘, job_category/subcategory 只能选树内词 (2) 源文本校验 — 岗位名必须出现在 title+content 中, 过滤幻觉 (3) Prompt 铁律 — "只提取明确出现的岗位, 严禁编造"

### Q6: "bad case 怎么回流的?"
> 线上 LLM 结果按 content_hash 缓存。每月抽样 50 条, 用 LLM-as-Judge 自动标注 + 人工审核, 按错误类型归入 bad case 池(missed/hallucinated/wrong_field/wrong_category)。每类 bad case 对应 Prompt 改动策略, 改完跑 25 条回归确保无退化后上线。SLA: 发现到上线 4 天。
