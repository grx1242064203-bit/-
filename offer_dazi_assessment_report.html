四、对抗性审查发现（按风险分级）

P0 · 新旧两套 HTTP 服务并存，飞书回调与业务 API 割裂 P0 架构

症状：仓库同时存在 callback_server.py（BaseHTTPRequestHandler，端口 8080，承载 /feishu/callback、/api/bind-wxpusher、/api/parse-resume、/api/profile）与 job_api/main.py（FastAPI，端口 8000，承载 /api/v1/* 业务路由）。

第一性原理：一个用户在不同触点（飞书内打开 vs 桌面端打开）的操作应该写入同一份用户状态，否则会出现"飞书侧绑定的 WxPusher / 画像"与"桌面端看到的画像"不一致。

对抗性场景：用户在飞书侧完成 onboarding 触发 /feishu/callback → 写入旧服务的存储；用户随后在桌面端调用 /api/v1/resume-profiles → 读新 API 的存储；两侧存储若未共享数据库，则画像丢失。

根因：迁移未完成。README 只介绍 job_api，但 callback_server.py 仍承担飞书回调这一不可替代职责；scripts/start_web.sh 启动的是第三套 web_setup.py，启动入口混乱。

证据：callback_server.py:35-41 BaseHTTPRequestHandler + .env；:550-555 监听 8080；job_api/main.py:94-105 仅注册 /api/v1 + /health，未注册 /feishu/callback；Makefile:6-16 dev-api 仅启动 job_api。
P1 · AutoFill 是导流页而非自研功能，与功能矩阵宣传口径不一致 P1 产品

症状：AutoFill.tsx 第 1 行注释"网申自动填写工具推荐页"，第 17 行"我们不重复造轮子，推荐使用成熟的浏览器插件自动填表"，实际是导流到牛客网申助手（nowcoder.com / Chrome 商店 / B 站教程）。

第一性原理：用户看到 "AutoFill 页面"在功能矩阵里被列为完整功能，预期是"我能用它自动填网申"。实际点击后是外链导流，价值交付依赖第三方插件，offer搭子 无法保证其可用性/隐私性/兼容性。

对抗性场景：牛客插件下架 / 收费 / 兼容性破坏时，offer搭子 的"网申自动填写"能力瞬间归零，但功能矩阵仍宣称具备此功能。

证据：AutoFill.tsx:1-20 含 NOWCODER_*_URL 三个外链常量。
P1 · DeepSeek-VL 命名与实际模型 ID 不一致，且无 fallback P1 命名/韧性

症状：截图功能 #8 写"DeepSeek-VL 图片 OCR"，代码注释与函数名也用"DeepSeek-VL"，但 DEEPSEEK_VL_MODEL = "deepseek-v4-flash-vision-exp"——实际是 DeepSeek v4 的视觉实验版，不是名为 DeepSeek-VL 的独立产品。

对抗性场景：DeepSeek 下线 v4-flash-vision-exp 实验模型（实验模型常被回收），代码硬编码无环境变量覆盖，调用全部失败；ocr_image 失败返回空串"不阻塞主流程"，但用户得到的是空简历解析结果，错误被静默吞掉。

优点：多策略重试 VL_STRATEGIES + last_vl_error 暴露错误，已具备一定韧性。

证据：llm_client.py:23-32 模型 ID 硬编码；:406-463 失败返回 ""。
P1 · ResumeUploader 前后端支持的图片格式不对齐 P1 一致性

症状：前端 ResumeUploader.tsx 接受列表是 .txt/.md/.pdf/.jpg/.png；后端 llm_client.py 的 mime_map 支持 png/jpg/jpeg/webp/bmp/gif。

对抗性场景：用户上传 .webp 截图简历（现代手机常见格式）→ 前端拒绝 → 用户以为系统不支持，但后端实际能处理。UX 死区。

证据：ResumeUploader.tsx:7-12 vs llm_client.py:421-425。
P2 · 拖拽冲突修复属补丁式，未抽象状态机 P2 可维护性

症状：KanbanBoard.handleDrop 内联处理同列/跨列/逆向三种情况，confirmReverse 弹窗确认。修复有效但未抽象出"合法转移图"。

对抗性场景：未来新增"已 Offer"状态后，需在 handleDrop 继续打补丁判定合法性；并发拖拽（用户在手机端和桌面端同时拖同一申请）无乐观锁/版本号，可能出现后写覆盖。

证据：KanbanBoard.tsx:46-88。
P2 · PDF 提取器无 OCR fallback，扫描版 PDF 静默失败 P2 健壮性

症状：pdf_extractor.py 用 PyMuPDF 提取文本，对扫描版 PDF（每页是图片）会返回空文本。

第一性原理：简历 PDF 中扫描版占比不低（尤其图片导出/老 PDF）。空文本会传给 LLM 解析，得到空画像。

建议：检测到提取文本为空且 PDF 有图像页时，自动走 ocr_image 路径降级。

证据：pdf_extractor.py:18-58 无 OCR fallback 分支。
P2 · RecruitmentCard 重试无退避，仅尽调可重试 P2 一致性

症状：重试按钮仅在尽调失败时出现，岗位匹配/简历解析失败无对应重试入口；重试无最大次数与指数退避。

对抗性场景：用户连续点重试 → 后端 LLM 调用被限流 → 级联失败。

证据：RecruitmentCard.tsx:264-289。

五、第一性原理审视总结

从第一性原理出发，"Offer搭子"作为求职管理工具的核心价值链是：发现岗位 → 解析简历 → 匹配推荐 → 投递追踪 → 邮件/日程闭环。逐项审视：

  • 发现岗位（功能 #1 搜索 + 飞书源表管线）：✅ 闭环成立，源表→同步→清洗→总表链路清晰。
  • 解析简历（功能 #6/7/8/9）：✅ 主路径完整，但扫描版 PDF/格式不对齐是脆点。
  • 匹配推荐（功能 #5）：✅ 适配器模式清晰。
  • 投递追踪（功能 #10/11 Kanban）：✅ 闭环成立，状态机抽象待加强。
  • 邮件/日程闭环（功能 #2/3）：✅ IMAP 接入 + 邮件转日程编排成立。
  • 网申自动填写（功能 #4 AutoFill）：⚠️ 价值交付外包给第三方插件，非自研能力。这是唯一"功能矩阵宣称但实际不掌握"的环节。

六、改进建议优先级

  1. [P0 立即] 合并新旧服务：将 /feishu/callback、/api/bind-wxpusher 迁移到 job_api/main.py，废弃 callback_server.py；统一 /api/parse-resume → /api/v1/llm/parse-resume，消除重复端点。同步更新 scripts/start_web.sh 与 README。
  2. [P1 短期] AutoFill 页面：在功能矩阵中标注"推荐工具"而非"自研功能"，或在页面顶部加显著免责声明"本页推荐第三方插件，能力与稳定性由第三方保证"。
  3. [P1 短期] DeepSeek-VL：模型 ID 改为环境变量 DEEPSEEK_VL_MODEL 可覆盖；增加 fallback 视觉模型（GLM-Vision/GPT-4V）配置项；ocr_image 失败时返回结构化错误而非静默空串。
  4. [P1 短期] ResumeUploader 前后端格式列表对齐：前端接受 .webp/.bmp，与后端 mime_map 一致。
  5. [P2 中期] pdf_extractor 增加扫描版检测与 OCR fallback 路径（复用 ocr_image）。
  6. [P2 中期] KanbanBoard 抽象"合法转移图"（states + allowed_transitions），handleDrop 查图判定，新增状态无需改逻辑；引入版本号做乐观锁。
  7. [P2 中期] 重试机制统一：所有异步失败 UI 都提供重试按钮 + 指数退避 + 最大次数。
  8. [P2 长期] README 目录结构过时（写"pages/ 占位 Jobs/Resume/Applications/Login"，实际有 Email/Schedules/AutoFill 等），需同步更新；增加架构图。

七、总体结论

Offer搭子 主体功能完善度良好（11 项中 8 项 ✅ 完整），数据管线主干清晰、定时调度与缓存机制完备、前后端 API 在 /api/v1/* 命名空间下对齐良好，是一个已具备交付能力的产品。从第一性原理审视，五条核心价值链中四条闭环成立，唯一例外是 AutoFill 的"网申自动填写"价值外包给第三方。

但对抗性审查暴露了一处 P0 架构断点（新旧服务并存导致飞书回调与业务 API 割裂）和若干 P1/P2 韧性缺口（命名不一致、格式不对齐、补丁式修复）。这些不影响当前 demo 可用性，但会在用户规模扩大或多端并发时显著放大风险。

建议优先完成 P0 服务合并后再做下一轮功能扩展；P1 项可在下一个迭代周期内完成；P2 项纳入技术债看板。

评估方法：第一性原理（从功能本质出发审视必备要素）+ 对抗性审查（边界/故障/不一致场景）
