三、新方案的风险与缺失

P1 · 用户失去飞书侧主动触达通道，需桌面端补齐 P1 功能真空

症状：删除 DailyRunner 后，原先通过飞书机器人推送给用户的 4 类主动通知全部消失：

  • 每日日报卡片（_send_daily_card，TOP3 岗位 + 直达链接）
  • 校招截止提醒（_check_deadline_reminders，截止前 3 天提醒）
  • 投递跟踪通知（_check_applied_jobs，已投递岗位关闭时通知）
  • WxPusher 微信日报（wxpusher.send_daily_summary）

第一性原理：求职是高时效场景（截止日期、面试通知、岗位关闭），用户不主动打开应用就会错过。原方案的飞书/微信推送是"推"模式，新方案退化为"拉"模式，依赖用户主动打开桌面端。

对抗性场景：用户安装桌面端后长期不开机/不打开 → 错过截止日期 → 投递失败 → 产品价值归零。

建议：桌面端需补齐等价的主动通知能力：系统通知（Tauri notification）、邮件提醒（已接 IMAP，可复用）、或浏览器通知。截止提醒尤其要在桌面端实现。

证据：daily_runner.py:208-240 推送逻辑均在 DailyRunner._run_with_lock 内。
P1 · 投递跟踪与截止提醒逻辑被一并删除，桌面端是否有等价能力？ P1 功能承接

症状：DailyRunner._check_deadline_reminders（查主表截止日期≤3天岗位并提醒）和 DailyRunner._check_applied_jobs（复查已投递岗位是否已关闭）是两个独立的"看护逻辑"，不依赖飞书机器人，本质上可以脱离推送独立存在。但它们当前耦合在 DailyRunner 类里，会随类一起被删。

第一性原理审视：这两个逻辑解决的是"用户投递后忘记跟进"的问题，与"是否用飞书机器人推送"是正交的。删除推送通道 ≠ 删除看护逻辑。

建议：把这两个逻辑提取为独立函数（check_deadlines() / check_applied_status()），改为查询 job_api 数据库（而非飞书用户表），结果通过桌面端系统通知或 KanbanCard 标记呈现。不要随 DailyRunner 一起删。

证据：daily_runner.py:393-516 两个看护方法当前直接读飞书用户表，需重构为读 job_api DB。
P1 · 用户 Onboarding 流程断链 P1 用户旅程

症状：原方案用户通过飞书机器人 onboarding（安装应用 → 拿到 feishu_base_token / feishu_table_id / feishu_open_id）完成注册和飞书表配置。删除 callback_server.py + onboarding.py 后，新用户如何注册、如何拿到 job_api 账号、如何关联桌面端没有清晰路径。

第一性原理："用户登录与画像绑定"是产品的入口，必须有等价替代。新方案下用户不再有飞书应用安装这一入口，job_api 必须提供独立的注册/登录/设备绑定端点（看 job_api/routers 是否已有 auth/users 路由）。

建议：梳理新方案下的用户旅程：下载桌面端 → 注册/登录 → 上传简历 → 看岗位 → 投递追踪。补齐 job_api 的 auth 路由，明确 token 颁发与设备绑定机制。

证据：onboarding.py 删除后，job_api/main.py:94-105 注册的路由列表需确认是否含 auth。
P2 · 飞书总表降级为"只读展示表"，用户无法在飞书侧改状态 P2 体验降级

症状：原方案用户可在飞书总表里直接改"申请状态"字段（未投递/已投递/面试中），DailyRunner 会回读这些状态做跟踪。新方案下总表是中心化管线的同步目标，用户在飞书侧的修改会被下一次同步覆盖。

第一性原理："27届校招汇总表"在新方案下是纯只读视图，用户只能看不能改。投递状态只能通过桌面端 Kanban 修改。这本身没问题，但要在飞书表顶部显著标注"本表为只读视图，投递进度请在桌面端管理"，避免用户误改后困惑。

建议：在 feishu_master_tables 写入时锁定关键字段为只读；或在飞书表顶部加说明行。

P2 · 数据更新频率从"实时/每日用户级"退化为"每日中心化一次" P2 时效性

症状：原方案 DailyRunner 每日为每用户跑一次匹配+写入用户表；新方案只跑一次中心化管线（8:00 增量），用户看到的总表是统一一份，更新频率 24h。

第一性原理：对"看岗位"场景，24h 延迟可接受（校招岗位不会分钟级变化）。对"投递状态跟踪"场景，用户在桌面端 Kanban 的修改是实时的（直接写 job_api DB），不影响。

结论：非阻塞，但要在用户预期里说明"飞书总表每日 8:00 后更新，最新进度请看桌面端"。

P2 · 11 项功能中 #4 AutoFill 与 #10 RecruitmentCard 重试在新方案下的状态 P2 功能确认

症状：桌面端功能"不变"，但其中两项依赖外部链路：

  • #4 AutoFill：本就是导流到牛客插件的推荐页，与飞书链路无关，新方案下不变，仍为推荐页（P1 命名偏差问题依旧存在）。
  • #10 RecruitmentCard 重试：调 getCompanyDueDiligence，走 job_api，不依赖 DailyRunner，不受影响。

结论：11 项桌面端功能在新方案下均可正常工作，无新增缺失。

五、迁移与改进建议优先级

  1. [P0 立即] 完成"减法"：删除 callback_server.py、bind_wxpusher.py、wxpusher_client.py、onboarding.py、DailyRunner 类、feishu_client.py 中用户侧方法（send_message/send_card/create_doc/share_with_user）。更新 scripts/crontab.example、scripts/start_web.sh、README、Makefile，移除对应启动项。
  2. [P0 立即] 拆解 DailyRunner：把 _check_deadline_reminders 和 _check_applied_jobs 的看护逻辑提取为独立函数，改为读 job_api 数据库（不读飞书用户表），纳入 run_daily_pipeline 末尾或独立 cron 任务，结果写入 notifications 表等桌面端拉取。
  3. [P1 短期] 桌面端补主动通知：Tauri 2 原生支持 notification API，在桌面端启动时检查未读 notifications 并弹系统通知；截止日期≤3 天的岗位在 KanbanCard 上加红色徽标。
  4. [P1 短期] 用户 onboarding 重设计：job_api 补 auth 路由（注册/登录/token 颁发），桌面端首次启动引导上传简历而非安装飞书应用。明确"用户如何获得 job_api 凭证"。
  5. [P1 短期] 飞书总表加只读说明：在 feishu_master_tables.py 写入时，于表顶部插入一行说明"本表为中心化同步视图，每日 8:00 更新；投递进度请在桌面端 Offer搭子 管理"。
  6. [P2 中期] 数据库一致性校验：删除双写后，做一次全量数据迁移，把原飞书用户表里的"申请状态/截止日期"等用户标记字段回写到 job_api DB，避免历史数据丢失。
  7. [P2 中期] 同步 11 项功能矩阵宣传口径：原评估报告中的 P1 项（AutoFill 命名偏差、DeepSeek-VL 命名不一致、ResumeUploader 格式对齐）仍需处理，不因方案变更而消失。

六、总体结论

新方案是一次健康的"减法"，评分 8.5/10（A-），较原方案 7.0/10（B+）提升 1.5 分。

新方案用"删 callback_server.py + 删 DailyRunner"一举解决了原方案最大的 P0 架构断点（新旧服务并存、状态层割裂），同时把架构从 4 层简化到 2 层、用户 onboarding 门槛大降、飞书 API 权限收敛、技术债显著下降。架构层面是一次明确改进。

代价是用户失去飞书侧的主动触达通道（日报/截止提醒/投递跟踪通知）。这部分能力本质与飞书机器人无关，应作为独立看护逻辑迁移到 job_api + 桌面端系统通知，而非随 DailyRunner 一起删。若不做这一步，会形成"用户安装后不开机就错过截止日期"的功能真空。

建议路径：先完成 P0 删除与看护逻辑迁移（这是新方案能否落地的关键），再做 P1 桌面端通知补齐与 onboarding 重设计。完成后此方案可达到 9.0+/10 的健康度。

原评估报告中关于 11 项桌面端功能的 P1/P2 缺陷（AutoFill 命名偏差、DeepSeek-VL 命名与无 fallback、ResumeUploader 格式不对齐、KanbanBoard 状态机抽象、PDF 无 OCR fallback 等）在新方案下依然成立，需独立处理，不因架构简化而消失。

评估方法：第一性原理（功能本质审视）+ 对抗性审查（功能真空/迁移断链/降级场景）
