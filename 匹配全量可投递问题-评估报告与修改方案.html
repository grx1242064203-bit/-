简历匹配「全量可投递」问题 — 评估报告与修改方案

项目：offer搭子（job_assistant）
现象：所有推荐岗位都被标记为「可投递」，无「推荐」或「强烈推荐」。
测试用例：西安交大硕士 + 华为/中兴实习 + IEEE 论文简历。
约束：本报告仅评估与方案设计，不修改任何代码。

一、结论速览

这是一个系统性缺陷，由「前端数据丢失 → 后端评分关键参数缺失 → 方向硬门槛误触发 → 全量分数被封顶」四个环节串联造成。核心不是评分算法本身算错，而是岗位方向键（cat_key / sub_key）在前端归一化时被剥离，导致 scorer 的 role 维度恒为 0，触发方向硬门槛把所有岗位总分压到 45 分（落在「可申请」区间）。

序号问题严重度定位文件
1前端 FitDirection 类型缺失 cat_key/sub_key，normalize 时剥离方向键致命job_workbench/src/api/llm.ts
2推荐接口调用不存在的方法 match_jobs_for_user，异常后降级走 score_job致命job_api/services/job_matcher_adapter.py
3fit_directions 缺方向键时 _match_role 无防御性反查，role 分恒为 0高scorer.py
4ROLE_GATE_THRESHOLD=40 偏高，边缘匹配易被误封顶中scorer.py
5缺少 fit_directions 结构与 role 分的生产日志，问题难发现低scorer.py / adapter

二、根因链还原

① LLM 解析简历→resume_parser 产出 fit_directions，含 cat_key/sub_key/category_name
② 前端接收→normalizeParsedProfile 只保留 direction/weight/evidence，剥离 cat_key/sub_key
③ 保存画像→fit_directions_json 入库时已无方向键
④ 构建 UserProfile→fit_directions 传给 scorer 时 cat_key=None / sub_key=None
⑤ _match_role 评分→job_tree.score_fit 返回 0 → role_score = 0
⑥ 方向硬门槛→role_score(0) < 40 → 总分被封顶为 45
⑦ 推荐等级→45 分落在 [35,55) →「可申请」→ 前端展示「可投递」

所有岗位无一例外走通这条链，因此全量都是「可投递」。

关键代码证据

证据 1：后端解析器确实产出了方向键，但前端类型不接收。

resume_parser.py _validate_fit_directions 在 L193-L223 把每个 direction 解析为树节点并写入 cat_key、sub_key、category_name：

"direction": entry.get("sub_name") or entry.get("category_name") or direction,
"cat_key": entry["cat_key"],
"sub_key": entry.get("sub_key"),      # 大类时为 None
"category_name": entry.get("category_name", ""),

但前端 FitDirection 接口（llm.ts L27-L32）只声明了 4 个字段：

export interface FitDirection {
  direction: string;
  weight: number;
  evidence?: string;
  description?: string;   // ← 无 cat_key / sub_key / category_name
}

且 normalizeParsedProfile（llm.ts L66-L74）显式只取这 4 个字段，方向键被丢弃。

证据 2：_match_role 依赖 cat_key/sub_key 构造 fit_entry（scorer.py L325-L332）：

fit_entry = {
    "type": "subcategory",
    "cat_key": fd.get("cat_key"),      # None
    "sub_key": fd.get("sub_key"),      # None
}
factor = job_tree.score_fit(fit_entry, job_entry)   # → 0.0

job_tree.score_fit（job_tree.py L157-L163）在 cat_key/sub_key 为 None 时返回 0.0，因此 role_score = 0。

证据 3：方向硬门槛封顶（scorer.py L630-L639）：

role_score = dim_scores.get("role", 0.0)        # 0
if role_score < ROLE_GATE_THRESHOLD:             # 0 < 40 → True
    if score > ROLE_GATE_CAP:                    # 45
        score = ROLE_GATE_CAP                    # 总分封顶 45

证据 4：分数到推荐等级的映射（scorer.py L645-L652）：

score >= 75 → 强烈推荐
score >= 55 → 推荐
score >= 35 → 可申请     ← 45 落在此区间
else       → 不建议

adapter 把「可申请」映射为 recommend_level = "applyable"，前端展示为「可投递」。

证据 5：matcher 方法名错误（job_matcher_adapter.py L145）：

top_jobs = matcher.match_jobs_for_user(user_profile, top_n=top_n, max_per_company=3)

而 UserMatcher 类只有 match(self, max_per_company, min_score)（user_matcher.py L255），match_jobs_for_user 是模块级函数（L307），不是方法。调用抛 AttributeError，被 L150-L152 捕获后 top_jobs = []，随后走 score_job 补齐逻辑——而 score_job 正是带方向门槛封顶的评分函数，于是全部岗位被压到 45。

三、修改方案（按优先级）

修复 1【致命 · 必须】前端保留 fit_directions 方向键

文件：job_workbench/src/api/llm.ts

  • 在 FitDirection 接口中增加 cat_key?: string、sub_key?: string | null、category_name?: string。
  • 在 normalizeParsedProfile 的 dirs 映射中透传这三个字段（原样保留，不做归一化裁剪）。

效果：方向键从 LLM → 前端 → 入库全程不丢失，_match_role 能正确计算 role 分。

修复 2【致命 · 必须】修正 matcher 方法调用

文件：job_api/services/job_matcher_adapter.py L145

  • 把 matcher.match_jobs_for_user(user_profile, top_n=top_n, max_per_company=3) 改为调用类方法 matcher.match(max_per_company=3)，或改为模块函数 match_jobs_for_user(user_profile, ...)。
  • 需核对 match() 与 match_jobs_for_user() 的返回结构是否与下游「补齐逻辑」的契约一致（含 score/recommend/reasons/dims）。

效果：推荐主路径不再抛异常降级，由 matcher 的预筛 + 评分产出有序结果，而非全量走封顶的 score_job。

修复 3【高 · 建议】scorer 增加防御性反查

文件：scorer.py _match_role（L320 附近）

  • 当 fit_dirs 中某项缺少 cat_key/sub_key 时，用 direction 名称调用 job_tree.resolve(direction_name) 反查得到 cat_key/sub_key，再参与 score_fit。
  • 反查失败（direction 不在树中）时，降级到旧的 role 关键词交集逻辑，而非直接得 0 分。

效果：即使前端或历史数据缺方向键，scorer 也能从方向名自救，避免 role 分恒为 0。这是对修复 1 的纵深防御。

修复 4【中 · 建议】调整方向门槛阈值

文件：scorer.py L44

  • 把 ROLE_GATE_THRESHOLD 从 40 下调到 30~35。当前 40 对「同大类匹配（系数 0.6）且权重偏低」的方向过于严苛，容易把边缘匹配压到可投递。
  • 可选：把 ROLE_GATE_CAP 从 45 上调到 50，避免一封顶就直接落到「可申请」下沿。
  • 需用真实简历样本做 A/B 校准，不要拍脑袋定阈值。

效果：降低方向门槛误触发率，让真正方向相近但非精确子类命中的岗位有机会进入「推荐」。

修复 5【低 · 可选】增加运行时监控日志

  • 在 _match_role 记录 fit_directions 的方向键完整率（多少项有 cat_key/sub_key）与最终 role_score，按 profile 采样打 INFO/WARN。
  • 在 adapter 记录 matcher 主路径是否走了异常降级（catch 块里加 logger）。
  • 上线后观察 role_score 分布与 recommend_level 分布，确认「强烈推荐/推荐」占比回到合理区间（建议 ≥30%）。

四、修复顺序与依赖

  1. 先做修复 1 + 修复 2（并行）：这两个是主因，修完后全量可投递现象应消失。
  2. 再做修复 3：对历史已入库、缺方向键的 resume_profiles 做兜底，避免老用户仍得 0 分。
  3. 最后做修复 4：用真实样本校准阈值，不要在没数据时拍脑袋改。
  4. 修复 5 可随修复 1-3 一起加，用于上线后验证。

五、验证方案

  • 单元验证：用含 cat_key/sub_key 的 fit_directions 对一个后端岗位跑 score_job，确认 role_score > 0 且总分不被封顶。
  • 回归验证：用测试账号 test@test.com / 123456 走完整网页流程（解析简历 → 保存 → 推荐），确认结果中出现「强烈推荐」和「推荐」。
